## 2. Тесты без LLM

Новый файл `tests/test_agent_pipeline_quality.py` — **40 тестов**, по каждому из
R1–R6 с отрицательными и граничными сценариями:

- **R6**: формат метки с/без названия серии; снятие метки с конца текста; снятие
  голой «Часть N из M»; упоминание названия проекта в середине предложения НЕ
  снимается (граничный случай); повторная генерация не дублирует метку; метка не
  добавляется для одной публикации и для `reply_thread` (другой проект).
- **R1**: число вызовов LLM ограничено `MAX_SHORTEN_ATTEMPTS`; текст **никогда**
  не обрезается механически (даже если модель не сокращает совсем); досрочная
  остановка, когда влезло с первой попытки; `shortening_failed` ставится только
  при реальном провале и не ставится при успехе; Editor даёт разную формулировку
  в этих двух случаях.
- **R2**: `_stem()` схлопывает «решения/решений/решение», «товаров/товара»;
  короткие слова (≤5 букв) не усекаются и не путаются («вывод» ≠ «выбор»);
  воспроизведена реальная ложная сработка из run-5-revision (словоформы) — больше
  не срабатывает; **отрицательный** сценарий (совсем другая тема) по-прежнему
  ловится — стемминг не глушит настоящую несвязность.
  (Для теста выбраны слова `не из LONG_SERIES_TITLE`: сам титул содержит
  «решения», что само по себе — отдельный, уже проверенный кейс исключения
  scaffolding.)
- **R3**: 5 формулировок анонса (включая `to be continued`) ловятся в последней
  части; та же фраза в НЕ последней части — это требуемый переход, не
  нарушение; `expects_sequel=True` отключает проверку; нейтральное упоминание
  слова «продолжение» (не о серии) не ловится; полный `editor_node` с LLM,
  которая говорит `approved=True`, всё равно даёт `editor_approved=False`.
- **R4**: 5 формулировок явной рекламы ловятся; обычный инженерный текст — нет;
  «гарантия» (предложения) не путается с «гарантир-» (обещание) — граничный
  случай; backstop работает не только для пилота; полный `editor_node` даёт
  `editor_approved=False`, даже когда LLM говорит «одобрено».
- Комбинированный тест: черновик с анонсом И рекламным обещанием одновременно,
  LLM всегда отвечает `approved=True` — полный граф не падает, доходит до
  `max_revisions`, `editor_approved=False`, `publication.status == "blocked"`.

### Итог честно: 0/2 одобрено — хуже, чем 4/5 в части 1. Почему, и это не регрессия безопасности

**Причина — не баг, а неподатливость модели.** В обоих прогонах, во ВСЕХ 4
версиях подряд, несмотря на явную обратную связь Editor на каждой доработке
(«Фраза "Продолжение следует" в последней части неуместна» — слово в слово,
каждый раз), Copywriter продолжал писать «Продолжение скоро» / «Продолжение
следует» в последней части. Более того, та же фраза («Продолжение скоро.»)
попадалась и в НЕ последних частях — похоже, модель усвоила её как общий
«знак конца поста», а не как осознанный анонс следующей части.

**Детерминированная защита сработала безотказно: 8 проверок Editor, 8 раз
поймано, 0 раз пропущено.** Ни разу анонс в последней части не прошёл
незамеченным. То же для длины: `shortening_failed` отмечался честно (run-1 v2/v4
пункт 2; run-2 v1–v4 пункты 2 и/или 3), и ни один такой текст не был одобрен.

## 4. Тексты и причины решений Editor

### run-1, финальная версия (v4, НЕ одобрено)

**1/3 (410 зн.)** AI Catalog Consultant: архитектура и уроки — часть 1 из 3

AI Catalog Consultant разделяет выбор товаров и семантические доказательства, разграничивая источники и методы. Используются Python ingestion, PostgreSQL 16, Python indexing, n8n для RAG и Telegram. LLM (gpt-4.1-mini) понимает запросы, выбор товаров — через SQL и ранжирование. Векторный поиск поддерживает доказательства, не выбор. Продолжение скоро.

**2/3 (667 зн., `shortening_failed=True`)** AI Catalog Consultant: архитектура и уроки — часть 2 из 3

Рассмотрим инженерные решения проекта на основе архитектуры. В AI Catalog Consultant используются структурированные данные из SQL для цен, наличия и характеристик, а не факты, сгенерированные LLM. Семантические доказательства через pgvector, выбор товаров структурирован и детерминирован. Пять закрытых инструментов без произвольных SQL-запросов, характеристики в трёх состояниях: yes, no, not_listed. Семантический фильтр удаляет неподдерживаемые жёсткие ограничения. Индексация инкрементальная с сохранением embedding. Telegram транспорт — тонкий адаптер без бизнес-логики. Продолжение — в следующей части.

**3/3 (442 зн.)** AI Catalog Consultant: архитектура и уроки — часть 3 из 3

Векторный поиск оказался недостаточным для выбора товаров, подтвердив необходимость структурированной фильтрации. Использование всего контекста каталога приводило к ошибкам транскрипции и неверным данным. Модель выдумывала числовые ограничения, блокируемые семантическим фильтром, но повторялись. Исправление reject-and-retry отменено. Ограничения зафиксированы. **Продолжение следует.**

фраза "Продолжение следует", что не соответствует требованию отсутствия анонса
после последней части» + `Part 3 promises a sequel...` (детерминированно) +

### Что подтвердилось в реальном использовании

- **R6 держится**: во всех 8 версиях (оба прогона) метка «{серия} — часть N из
  3» — ровно один формат, всегда в начале. Старой путаницы (в конце, без
  названия, несогласованно) не наблюдалось ни разу.
- **R2 не даёт ложных срабатываний**: ни в одном из 8 прогонов Editor не
  сообщил «shares almost no subject matter» ошибочно.
- **R4 (мягкая часть) работает**: «неподтверждённое обещание точности и
  надёжности» поймано семантически Editor'ом в обоих прогонах — именно то, что
  просил промпт-апдейт; детерминированный backstop (100%, «гарантир-» и т.п.) в
  этих 2 прогонах не потребовался — explicit-рекламных фраз модель не писала.
- **R5** не проявился ни разу в этой выборке ни в плюс, ни в минус —
  недостаточно данных, чтобы судить.
- **R1/R3 работают как защита, но не как гарантия качества генерации** — см.
