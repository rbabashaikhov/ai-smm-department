## 3. Контент-план (Strategist, run-normal)

**Серия:** «Технический разбор AI Catalog Consultant: от задачи до уроков». Стратегия
`reply_thread` (выбрана агентом сам; см. дефект D1). Аудитория — разработчики, data/AI
инженеры, техменеджеры. Цель — почему и как построен проект: разделение источников
истины, архитектура, ограничения.

1. **Постановка задачи и ключевой принцип** — LLM не источник каталожной истины; датасет, статус, 4/15 и 7/8.
2. **Инженерные решения и архитектура** — SQL-выбор vs vector evidence, 5 закрытых инструментов, yes/no/not_listed, semantic guard, тонкий Telegram.
3. **Ошибки, ограничения и уроки** — vector search недостаточен, whole-catalog context, invented constraints, reject-and-retry откатан, 4/15 и 7/8.

Все key_facts плана сверены с KB — выдуманных нет. Угол «zero-item trap» и
«подешевле» из `content_angles.md` не использован.

## 4. Три текста (финальная версия v4 после 3 доработок; Editor: не одобрено)

**1/3 (347 зн.)** AI Catalog Consultant решает задачу точных ответов по каталогу, отделяя LLM от источника фактов. Цены, наличие и характеристики берутся из PostgreSQL, выбор продуктов — детерминированный Python, а LLM помогает понять запрос и сформулировать ответ. Проект — MVP, ориентированный на реальный каталог телевизоров, с подтверждённым статусом и тестами.

**2/3 (400 зн.)** Исходя из задачи, архитектура разделяет выбор товаров и семантическое подтверждение. Векторный поиск используется лишь для поиска подтверждающих фрагментов, а выбор товаров — через структурные SQL-запросы и детерминированный Python. Система включает пять закрытых инструментов, три состояния признаков и semantic guard для удаления выдуманных ограничений. Telegram — тонкий адаптер без бизнес-логики.

**3/3 (444 зн.)** Анализ ошибок выявил, что векторный поиск недостаточен для выбора товаров, нужна структурированная выборка с семантическими доказательствами. Использование всего контекста каталога приводило к ошибкам транскрипции. Модель могла выдумывать жёсткие ограничения, которые semantic guard удалял, но формулировка могла их повторять. Решение reject-and-retry отменено. Ограничения задокументированы, строгая приёмка — HOLD 4/15, demo suite — 7/8 PASS.

### Оценка качества (ручная сверка с KB + скан 141 текста всех прогонов)

- Числа: 0 чисел вне KB во всех 141 текстах. 4/15 и 7/8 приводятся вместе, как требует `evaluation.md`.
- Финальные тексты фактологически корректны. Слабые места: «точных ответов» (1/3) — мягкое преувеличение; «с подтверждённым статусом и тестами» (1/3) — пустая фраза; 2/3 — перечень без объяснения «почему»; semantic guard и разделение SQL/LLM повторяются во всех трёх частях; нет конкретики (PS5 → HDMI 2.1, «подешевле»), которая есть в KB.
- Не пойманы Editor'ом в промежуточных версиях: «Отказ от reject-and-retry обусловлен сложностями реализации» (выдуманная причина; в KB «failed and was reverted»), «ограничения … учтены в итоговом продукте» (намёк на устранение), «обеспечивая точность и надёжность» ×5, «три состояния признаков … улучшают точность», утечка служебного «Главный тезис: …» в текст.
- Явная реклама («лучший», «100%», «гарантированно») — только во внедрённом тестовом черновике; Editor её поймал.
